# Gather Public Website

This repository contains the public website for **Gather**, a food-rescue and volunteer-impact platform initially focused on Colorado.

The authenticated Gather application is a separate product. This repository is for the public-facing website and marketing/web experience.

## Core purpose

Gather connects:

1. Businesses with appropriate surplus food
2. Recipient organizations that can use that food
3. Student and community volunteers who help move it

Gather's mission is to:

**Reduce food waste. Fight hunger. Make helping your community easier.**

A major focus is making meaningful community service accessible to students while creating trustworthy records of completed service.

Adults may volunteer too.

## Public website goals

The website should:

* explain Gather clearly
* establish legitimacy and trust
* communicate the mission
* make people want to participate
* attract volunteers
* attract businesses
* attract recipient organizations
* attract schools and service programs
* attract donors, sponsors, foundations, and community partners
* communicate verified impact transparently
* eventually drive app downloads
* provide a clear route to the authenticated Gather application

The website must never feel like a blown-up mobile app.

## Truthfulness

Never invent:

* partnerships
* sponsors
* testimonials
* statistics
* impact totals
* app-store availability
* payment functionality
* school integrations
* NHS integrations
* organization endorsements
* team members
* awards
* dates or milestones that have not been supplied
* functionality that is not confirmed

Do not imply Gather service records are automatically accepted by schools, NHS chapters, scholarships, or service programs.

Do not display fake App Store or Google Play links.

When real impact data is unavailable, create intentional early-stage or coming-soon states rather than fake numbers.

## Approved visual direction

The visual direction is **inviting, sophisticated, active, warm, and highly professional**.

It should feel like a real, modern organization with strong creative direction.

It must NOT resemble:

* a generic nonprofit template
* a Wix template
* a generic SaaS landing page
* a school project
* a dashboard enlarged for desktop
* an AI-generated website
* a huge collection of cards
* an outdated charity site

### Visual personality

Use a refined editorial/documentary approach centered on real food rescue and community action.

The approved direction uses:

* deep forest / near-black green as a major anchor
* warm natural off-white backgrounds
* fresh green accents used intentionally
* warm food-derived accent colors where useful
* strong real-world photography
* restrained graphic elements
* generous negative space
* elegant editorial compositions
* clean, modern interface details

Photography should provide much of the site's natural color.

Avoid overly cute nonprofit graphics.

Avoid fake Gather-branded vans, uniforms, merchandise, or fabricated operational scenes.

## Typography

Typography should feel editorial and modern.

Use:

* a character-rich display face where appropriate
* a highly legible modern sans-serif for functional text

Headlines should feel confident but **must not become absurdly oversized**.

Do not use giant viewport-filling typography simply because it is fashionable.

Typography should remain inviting, readable, and balanced with photography.

## Language

Writing should feel:

* human
* optimistic
* confident
* concise
* welcoming
* credible
* community-oriented

Language such as **“Join the movement”** can appear where appropriate.

Avoid:

* guilt-heavy fundraising language
* pity-based messaging
* exaggerated startup language
* corporate jargon
* overly sentimental charity copy

## Motion system

Motion is a major part of the website, but every animation must have a purpose.

Use motion to improve:

* storytelling
* hierarchy
* understanding
* responsiveness
* emotional pacing
* transitions between ideas

Good motion patterns include:

* arrows or lines smoothly extending/opening on hover or entry
* image reveals
* masked photography transitions
* subtle parallax
* controlled scroll-linked movement
* sticky storytelling sections
* text/image choreography
* hover transformations
* responsive section transitions
* subtle navigation state changes
* progressive diagrams
* animated impact states

Do NOT use:

* scroll-jacking
* excessive spring/bounce animations
* random floating objects
* animation on every element
* distracting cursor effects
* heavy WebGL simply for spectacle
* transitions that delay navigation
* motion that compromises readability
* gratuitous page-loader animations

Plan animation before implementing it.

Every significant animated section should have:

1. its purpose
2. trigger
3. start/end state
4. easing/timing
5. mobile behavior
6. reduced-motion fallback

Prefer CSS transforms, opacity, SVG, IntersectionObserver, and lightweight motion techniques.

Use a heavier animation dependency only where it clearly improves the experience.

Respect `prefers-reduced-motion`.

## Responsive design

Mobile is not a smaller desktop layout.

Every major section must intentionally consider:

* reading order
* typography
* photography crop
* image positioning
* touch interaction
* section height
* motion simplification
* navigation
* spacing
* CTA placement

Desktop may be more cinematic.

Mobile should remain equally designed and polished.

Avoid desktop compositions that collapse awkwardly into stacked cards.

## Page identities

Pages must share a brand system but should not all reuse the same hero and section layout.

### Home

Tell the overall Gather story.

Communicate:

* mission
* the three sides Gather connects
* why the system matters
* who can participate
* a glimpse of the rescue journey
* a glimpse of impact
* pathways deeper into the site
* an appropriate support opportunity

The homepage should be memorable but not enormous.

### How It Works

This should be one of the most visually ambitious pages.

The real conceptual rescue sequence is approximately:

surplus becomes available
→ receiving destination / eligibility
→ opportunity becomes available
→ volunteer claims it
→ pickup / handoff
→ transport
→ delivery
→ recipient confirmation / completion
→ impact and service activity recorded

Do not reduce this page to a generic row of numbered icon cards.

Prefer a spatial or scroll-driven rescue journey.

### Get Involved

Help visitors understand where they belong:

* volunteer
* business
* recipient organization
* school/program
* supporter

Do not default to five repetitive cards.

Create an active audience-selection experience.

### Volunteers

Emphasize:

* nearby rescue opportunities
* participation around someone's schedule
* tangible local impact
* completed rescue verification
* service activity records
* personal impact

Strong Download Gather pathway.

### Businesses

This page should feel especially operational and professional.

Explain:

* making surplus available
* information businesses provide
* pickup coordination
* handoff
* completion confirmation
* eventual impact visibility

Primary actions may include:

* Join as a business
* Talk to Gather

Respect business operators' time.

### Recipient Organizations

Focus on:

* receiving preferences
* appropriate food
* rescue visibility
* coordination
* confirmation
* safety
* impact

Maintain dignity and operational clarity.

### Schools & Programs

Explain how Gather can potentially help:

* students
* schools
* NHS chapters
* service clubs
* advisors
* community programs

Possible themes:

* trustworthy service records
* participating students
* opportunities
* program impact
* community goals

Never imply official integrations or universal acceptance.

### Impact

Give this page its own visual identity.

Eventually it can surface verified metrics such as:

* food rescued
* rescues completed
* volunteer hours
* participating businesses
* recipient organizations

Never invent these values.

Early-stage states should explain what Gather intends to measure and why transparent reporting matters.

### About

Gather was started by students.

Tell that story naturally without turning the page into a biography wall.

Themes may include:

* why Gather began
* mission
* beliefs
* Colorado roots
* community
* direction for the future

Never invent founder details or accomplishments.

### Support

Financial support should be prominent across the ecosystem without every page feeling like a fundraising page.

Support may eventually include:

* individual giving
* companies
* sponsorships
* foundations
* community partnerships

Messaging can include ideas such as:

* Join the movement
* Power the next rescue
* Help Gather rescue more food

Do not invent dollar-to-impact ratios.

Do not implement fake payment behavior.

### Download

Eventually support:

* iPhone
* Android
* web app
* QR code

Until real destinations exist, use polished Coming Soon states.

## Sponsors and partners

Design partner recognition so it can eventually feel prestigious and intentional.

Do not create a giant generic logo wall.

Never display fake logos.

The section should be hideable until real organizations exist.

## Components

Avoid excessive card-based design.

Cards may be used where they genuinely help information architecture, but do not make every section a rounded rectangle.

Prefer:

* editorial layouts
* photography
* spatial relationships
* controlled asymmetry
* typography
* lines and directional graphics
* open compositions
* purpose-built interactive elements

## Buttons and CTAs

Buttons should feel refined and tactile.

Plan hover interactions intentionally.

Directional CTAs may use an arrow whose shaft/line smoothly extends or opens during interaction.

Do not make every CTA a huge pill.

Maintain clear hierarchy between primary, secondary, and text actions.

## Header

The header should feel elegant and restrained.

It may transition between transparent/overlay and solid states when appropriate.

Do not clutter it.

Support should remain easy to find.

## Performance

Target an excellent production website.

Prioritize:

* Next.js
* React
* TypeScript
* semantic HTML
* responsive images
* `next/image`
* server components where useful
* minimal client JavaScript
* minimal layout shift
* strong LCP
* good Core Web Vitals
* lazy loading below the fold
* optimized fonts
* efficient animation

Do not sacrifice performance for visual spectacle.

## Accessibility

Target WCAG AA.

Requirements include:

* keyboard navigation
* visible focus states
* semantic landmarks
* proper button/link semantics
* appropriate contrast
* meaningful alt text
* sensible heading hierarchy
* accessible menus
* reduced-motion behavior
* sufficient touch targets

Never make essential content dependent solely on hover or animation.

## SEO

Use:

* proper metadata
* semantic structure
* meaningful page titles/descriptions
* Open Graph metadata
* sitemap
* robots configuration
* structured data where truthful and useful

Do not generate SEO spam.

## Implementation philosophy

Do not broadly improvise visual design.

Before implementing a major page:

1. understand the supplied design reference
2. identify the page's visual concept
3. identify motion behavior
4. identify desktop behavior
5. identify mobile behavior
6. identify accessibility requirements
7. identify what content is confirmed versus placeholder

Build page-by-page in controlled phases.

Do not redesign already approved areas while implementing unrelated work.

When asked to make a targeted change, preserve everything outside its scope unless technically necessary.

## Review workflow

Development should use Git and Vercel Preview deployments.

Major page work should be reviewed visually before being treated as complete.

Expect iterative refinement after implementation.

Do not assume the first coded version is final.

## Current state

The repository has only the clean application foundation.

Do not begin independently designing or building the full website until explicit implementation instructions and visual references are provided.
